# FootballManager שלב 9

הפתרון כולל את לקוח WPF הראשון, אתר הלקוח השני, לקוח Android ב־.NET MAUI, שירות CoreWCF ופרויקט FootballManager.Contracts המשותף. מסד ההדגמה נמצא ב־FootballManager.WCF/Data/FootballManager.accdb וכולל את הטבלאות ונתוני הדמה של C1–C4. באתר נכנסים בדף הבית ופותחים את אזור התוכן בכתובת /content.html כדי לנהל שחקנים, קבוצות, משחקים, העברות וסטטיסטיקות לפי התפקיד. השרת אוכף הרשאות על אותן פעולות בשלושת הלקוחות.

## הפעלה מקומית ב־Windows

נדרשים .NET 9 SDK ו־Microsoft ACE OLE DB 16.0 בגרסת 64 סיביות. מחלצים את קוד המקור לתיקייה מקומית שיש בה הרשאת כתיבה. מתיקיית הפתרון מפעילים ב־PowerShell:

```powershell
dotnet build .\FootballManager.WPF.sln
.\Start-Server.ps1
```

משאירים את השירות פועל. מחלון PowerShell שני, באותה תיקייה, מפעילים את הלקוח:

```powershell
dotnet run --project .\FootballManager.WPF\FootballManager.WPF.csproj
```

כתובת החוזה היא http://localhost:5152/FootballManagerService והלקוח השני זמין ב־http://localhost:5152/. שני הלקוחות פועלים מול אותו מופע שרת. רק השרת פותח את קובץ Access.

## התנסות ביכולות הקיימות ובסקאוט AI

1. נכנסים ל־WPF עם DemoManager ופותחים **העברות וסטטיסטיקות** בדשבורד. בשתי הכרטיסיות יש רשימה, טופס ופקודות לשליפה, הוספה, עדכון ומחיקה דרך WCF. לאחר שמירה הרשימה נטענת מחדש מהשירות.
2. אחרי שמירת העברה, נכנסים עם DemoPlayer. כפתור **בדיקת הרשאה להעברה** שולח אותה בקשת שמירה דרך WCF ומציג `403 Forbidden`. נתוני ההעברה אינם משתנים. Admin ממשיך לנהל משתמשים ואינו מורשה ל־C4.
3. עם DemoPlayer פותחים **סקאוט AI**, בוחרים שחקן ולוחצים **נתח שחקן**. השירות בודק את ה־Session והתפקיד בשרת, שולף את הפרופיל הציבורי מ־Access, שולח לספק AI מהשרת בלבד ומציג את התשובה. אין חיבור למסד מהמסך ואין שמירת ניתוח במסד.
4. עם DemoManager או Admin פותחים את אותו מסך ולוחצים על אותה פעולת ניתוח: WCF מחזיר `403 Forbidden`. ללא Session השירות מחזיר `401 Unauthorized`. גם כשאין מפתח, רשת או תשובת AI, המסך מציג הודעה ונשאר פתוח.
5. במסכי WPF הקיימים אפשר לבדוק את הכניסה של C1, יכולות C2 ו־C3 ואת ה־CRUD של C4.

## הגדרת שירות AI בשרת

גם ניתוח הסקאוט וגם הצ׳אט משתמשים כעת ב־Gemini דרך השרת. יש להגדיר את `FOOTBALLMANAGER_GEMINI_API_KEY` במשתני הסביבה של המשתמש במחשב שמריץ את WCF, ואז להפעיל את `Start-Server.ps1`. המפתח אינו נמצא בקוד, ב־WPF, במסד או באתר.

## בדיקת הרשאות בדפדפן

פותחים **תוכן המערכת ← העברות**. אורח רואה 401, ומשתמש שמחובר כ־Player רואה 403. ההודעה מציגה את הקוד מתשובת השרת. חשבון Manager רואה את הרשימה ויכול לערוך העברה. אפשר לרענן את הדף ולמצוא את אותה העברה בחלון WPF תחת **העברות וסטטיסטיקות**.

## בינה מקומית להדגמה

אפשר להפעיל את הצ׳אט והסקאוט עם Gemma 3 שרץ בשירות HTTP מקומי נפרד. מורידים ומחלצים את [llama.cpp ל־Windows x64 CPU](https://github.com/ggml-org/llama.cpp/releases/download/b12556/llama-b12556-bin-win-cpu-x64.zip), ומורידים את [מודל Gemma 3 4B](https://huggingface.co/ggml-org/gemma-3-4b-it-GGUF/resolve/d0976223747697cb51e056d85c532013931fe52e/gemma-3-4b-it-Q4_K_M.gguf). הסקריפט מפעיל את שני השירותים ויוצר מפתח זמני לשרת.

```powershell
.\Start-LocalAi.ps1 -LlamaServer 'C:\AI\llama\llama-server.exe' -Model 'C:\AI\gemma-3-4b-it-Q4_K_M.gguf'
```

מחלון שני מפעילים WPF. נכנסים כ־DemoPlayer, פותחים **צ׳אט בינה** ושואלים על השחקנים ברשימה. במקביל אפשר לפתוח את האתר בדפדפן עם חשבון נפרד.

## צ׳אט Gemini ב־WPF

בחלון צ׳אט בינה משתמש Player שולח שאלה דרך WCF. השרת מזהה את המשתמש, טוען שחקנים ומועדפים מ־Access, מחזיק היסטוריית שיחה נפרדת לכל משתמש בזיכרון ופונה לספק הבינה. הוספה למועדפים מתבצעת בבקשה מפורשת כשיש שחקן יחיד שתואם למזהה שהחזיר המודל ולשם המלא בשאלה או בתשובה הקודמת. אורח מקבל 401 ותפקיד אחר מקבל 403. שירות הבינה משמש את WPF דרך השרת.

להפעלה יוצרים מפתח API בחשבון Google AI Studio של בעל הפרויקט ומגדירים בשרת FOOTBALLMANAGER_GEMINI_API_KEY. מפעילים מחדש את השרת. המודל מוגדר ב־`Gemini:Model` בהגדרות השרת, וכרגע הערך הוא `gemini-3-flash-preview`. ללא מפתח אמיתי מתקבלת 503. אין לשמור את המפתח בקוד, במסד או בקובץ ההגשה.
## סיסמאות להדגמה מקומית

המסד מכיל גיבובי סיסמאות ב־Users.PasswordHash. הסיסמאות נמסרו בנפרד בחבילת C2. כדי לקבל סיסמאות הדגמה חדשות, עוצרים את השירות ומריצים על עותק עבודה מקומי את הפקודה הבאה. היא מקצה סיסמאות לשלושת חשבונות ההדגמה ומציגה אותן פעם אחת. לאחר מכן מפעילים שוב את השירות.

```powershell
dotnet run --project .\FootballManager.WCF\FootballManager.WCF.csproj -- --prepare-demo-accounts
```

## Android

לבניית הפתרון כולו נדרשים .NET 9 SDK, workload בשם `maui-android`, ‏JDK 17, ‏Android SDK 35 ו־Build Tools. לקוח הטלפון כולל חשבון ותוכן מסבבים 1 עד 3 ושולח בקשות SOAP לאותו WCF שמשמש את החלון.

```powershell
dotnet workload install maui-android
dotnet build .\FootballManager.Android\FootballManager.Android.csproj
adb devices
adb reverse tcp:5152 tcp:5152
```

היישום עובד באמולטור Android או במכשיר מחובר ב־USB עם Android Debug Bridge. מתקינים באמצעות `adb install -r` את `il.school.footballmanager-Signed.apk` מתיקיית הבנייה של Android, ופותחים את FootballManager. אם מחוברים כמה מכשירים, מציינים את המכשיר ב־`adb -s <serial>`. גישור USB מפנה את `localhost:5152` במכשיר לשרת שעל המחשב שבו פועלים האתר ו־WPF.

ב־Android נכנסים כ־Player, מוסיפים שחקן למועדפים ופותחים את **המועדפים שלי** כדי לראות את הרשומה שנשמרה. לחיצה על **משחקים ותוצאות** מציגה 401 לאורח ו־403 לאדמין. מאמן יכול לערוך שחקנים, קבוצות, סגלים ומשחקים.

## שיעור ראשון · מרשימת השחקנים עד Access

1. פותחים ב־WPF את רשימת השחקנים ולוחצים **חפש**. ב־`MainWindow.xaml.cs` רואים שהאירוע `SearchPlayers_Click` מפעיל את `RefreshPublicPlayersAsync`. היא קוראת את החיפוש מהמסך.
2. ב־`WcfServiceClient.cs` קוראים את `GetPlayersAsync`. היא שולחת את המסננים לכתובת `http://localhost:5152/FootballManagerService` דרך חוזה WCF. `localhost` הוא המחשב שעליו רץ השרת.
3. בשרת, `FootballManagerService.GetPlayers` מקבלת את הבקשה ובודקת את טווח הדירוג. היא מעבירה את המסננים אל `AccessFootballRepository.GetPlayers`.
4. `AccessFootballRepository` קורא את טבלת `Players` במסד `FootballManager.WCF/Data/FootballManager.accdb`. התוצאה חוזרת כאוסף `PlayerDto`, כאשר כל אובייקט מכיל את הנתונים של שחקן אחד.
5. חזרה בחלון, `PublicPlayersList.ItemsSource` מקבל את הרשימה שחזרה ומציג אותה.

לתרגול, חפש שחקן לפי חלק משם המשפחה ועקוב אחרי `searchText` לאורך התחנות. אחר כך הסבר במילים שלך מי שולח את הטקסט, מי מחליט אם הבקשה תקינה, ומי מריץ את ה־SQL.

## נתוני כדורגל ממקור חיצוני

בדף הבית פותחים **ליגות והרכבים**. האתר קורא לשרת FootballManager, ורק השרת קורא ל־API-Football. במסך בוחרים את שנת תחילת העונה. עונת 2026/27, למשל, מוצגת כ־2026. בוחרים משחק כדי לראות הרכב רשמי שפורסם אצל הספק, או בוחרים קבוצה כדי לקרוא את הסגל הנוכחי שלה.

המסך נפתח בעונת 2024, העונה האחרונה הזמינה במנוי החינמי שנבדק. אם הגישה לעונות אחרות משתנה, אפשר לעדכן את `FootballFeed:DefaultSeason` ב־`FootballManager.WCF/appsettings.json` או לבחור עונה במסך.

לפני הפעלת השרת מגדירים בחלון PowerShell 7 את `FOOTBALLMANAGER_API_FOOTBALL_KEY` עם `Read-Host -MaskInput`. לא שומרים את המפתח בקוד.

```powershell
$env:FOOTBALLMANAGER_API_FOOTBALL_KEY = Read-Host 'API-Football key' -MaskInput
.\Start-Server.ps1
```

תצוגת המערך מציירת עמדות כדורגל ומופרדת מההרכבים הרשמיים. הנתונים החיצוניים נקראים לתצוגה ואינם משנים נתונים ב־Access.

### תוכנית הרכב אישית

נכנסים באתר בחשבון Manager, פותחים **ליגות והרכבים**, טוענים ליגה ועונה ובוחרים משחק. תחת **תכנון הרכב למאמן** בוחרים אחת משתי הקבוצות במשחק ופותחים תוכנית. בוחרים מערך, שוער, עוד עשרה פותחים ועד 12 מחליפים. אפשר להעביר שחקן מהספסל להרכב ולשמור. השרת מוודא שהקבוצה משתתפת במשחק ושכל שחקן נבחר מהסגל פעם אחת בלבד.

תוכנית נשמרת בקובץ פרטי בשרת לפי מזהה החשבון, המשחק והקבוצה. ברירת המחדל היא תיקיית FootballManager/Lineups תחת LocalAppData. החשבונות וההרשאות עדיין נקראים מ־Access. הרכב שפורסם על ידי הספק מופיע בנפרד מתוכנית המאמן.

**בקש המלצת AI** שולח לשרת את התוכנית שמוצגת כרגע. אם הרכב היריבה וסטטיסטיקת העונה זמינים, השרת מוסיף נתוני שוער ומועמדים מהספסל. כשהספק לא פרסם אותם, הניתוח מקבל סימון של נתון חסר. ההמלצה מופיעה כטקסט, ושינוי הרכב מבוצע רק על ידי המאמן. הבינה משתמשת באותה הגדרת Gemini או ספק מקומי שכבר משמשת את הפרויקט.
